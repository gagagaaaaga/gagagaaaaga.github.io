How six layers took a service from 71.9% to 99.89% uptime

The resilience package runs one deliberately brutal 20-minute stress test against six setups. Each setup adds one idea to the last: more servers, more zones, more load balancers, smarter retries, and finally a system that repairs itself. Every number on this page comes from that code, averaged over 20 runs.

The stress test

Every setup lives through the same bad 20 minutes

Traffic runs at 60 requests per second, 90,000 requests per run. A second counts as downtime when more than 10% of its requests fail. Total capacity starts at 180 requests per second in every setup, so the differences come from how that capacity is arranged, not how much of it there is.

Step 1

1 big server

One machine handles all 180 requests per second behind one load balancer. Every crash is a full outage until a human restarts the server, and the zone outage takes everything down too.

The biggest cause of failure is "no healthy server": the time spent waiting for the on-call engineer.

chaos.py · Operator
# The on-call engineer: gets paged, investigates, restarts the box.
if (server.state == CRASHED and waited >= self.crash_repair_time) or \
        (server.error_rate and waited >= self.gray_repair_time):
    server.repair()      # 90 s for a crash, 150 s for a gray failure
Step 2

6 servers, 1 zone

The same capacity split into six servers of 30 requests per second. A crash now removes a sixth of the capacity instead of all of it, and failed requests drop by a third. Health checks pull a dead server out of rotation after two failed pings.

Downtime got worse, though, from 355 to 437 seconds. Six machines break six times as often, and nothing retries a failed request, so every crash leaks errors to users for the few seconds before health checks notice. The zone outage still takes everything, because all six servers sit in one building.

health.py · HealthChecker.run
for server, healthy in self._healthy.items():
    ok = server.ping()
    if ok == healthy:
        self._streak[server] = 0
        continue
    self._streak[server] += 1
    # 2 failed pings in a row to remove, 2 good ones to re-add
    threshold = self.healthy_threshold if ok else self.unhealthy_threshold
    if self._streak[server] >= threshold:
        self._healthy[server] = ok
Step 3

6 servers across 3 zones

Two servers in each of three zones. When zone-a loses power, four servers in zone-b and zone-c keep running. Users still get nothing, because the only load balancer lives in zone-a.

Exactly 9,000 requests are lost to "load balancer down": 150 seconds at 60 requests per second. Spreading servers is not enough when the load balancer is itself a single point of failure.

    # A load balancer is a machine too: it goes down with its zone.
    return self.zone.up
Step 4

A load balancer in every zone

Each zone gets its own load balancer, and DNS hands clients the address of every healthy one. When zone-a fails, DNS drops its balancer within the 5-second TTL. Zone-outage losses fall from 9,000 requests to 40.

Each balancer prefers servers in its own zone and spills over to other zones when local ones are full or down. What is left: errors from crashes before health checks catch them, and gray failures, which health checks never catch because the server still answers pings.

load_balancer.py · DnsFrontend
def tick(self, now):
    if now % self.ttl == 0:              # clients re-resolve every TTL
        healthy = [lb for lb in self.balancers if lb.available]
        self.answer = healthy or list(self.balancers)

def route(self, now):
    self._rr = (self._rr + 1) % len(self.answer)
    lb = self.answer[self._rr]
    if not lb.available:                 # cached answer, dead balancer
        return "load balancer down"
    return lb.route(now)
Step 5

Retries and circuit breakers

When a request fails, the load balancer retries it on up to two other servers. A circuit breaker watches each server's real requests: three failures in a row and the server gets no traffic for 10 seconds, then one trial request decides whether it comes back.

Server errors drop from 4,945 to zero and downtime falls from 343 to 107 seconds. The remaining failures are all overload during the traffic spike: demand equals the starting capacity, so any broken or isolated server leaves too little room.

load_balancer.py · LoadBalancer.route
for attempt in range(1 + self.retries):
    candidates = self._candidates(now, tried)  # healthy, breaker closed
    if not candidates:
        break
    server = self._pick(candidates)
    tried.add(server)
    try:
        server.handle(self.rng)
    except Overloaded:
        reason = "overloaded"            # shed load, server isn't broken
        continue
    except ServerError:
        reason = "server error"
        if breaker:
            breaker.record_failure(now)  # 3 in a row opens it
        continue
    return None                          # served
Step 6

A self-healing autoscaler

Every 5 seconds the autoscaler replaces crashed servers and servers the circuit breakers flagged, keeps at least two servers in every healthy zone, launches extra servers in the surviving zones during the outage, and adds servers ahead of the traffic spike. New servers take 8 seconds to boot and must pass health checks before they get traffic.

Failed requests fall from 4,490 to 102, and downtime from 107 seconds to 4. The lower chart shows the server count following the load: it dips when zone-a goes dark, refills in the other zones, and climbs to 10 for the spike.

autoscaler.py · Autoscaler.step
# 1. Self-heal. A server in a failed zone isn't broken itself, so it stays.
for server in list(cluster.servers):
    if server.state == CRASHED or (server in suspects and server.zone.up):
        cluster.terminate(server)

# 2. Every healthy zone keeps a minimum footprint.
for zone in healthy_zones:
    for _ in range(self.min_per_zone - len(self._usable(zone))):
        self._launch(zone, now)

# 3. Scale out to meet demand, filling the emptiest zone first.
if usable < want:
    for _ in range(min(want - usable, self.max_launch)):
        zone = min(healthy_zones, key=lambda z: len(self._usable(z)))
        self._launch(zone, now)

Use it

Run it yourself

Standard-library Python 3.8+, nothing to install. The source code lives in the resilience/ package of the project repository.

python -m resilience                  # comparison table, 5 runs
python -m resilience --seeds 20       # the numbers on this page
python -m resilience --json out.json  # full results and timelines
python -m unittest discover -s tests  # 15 tests

Change the experiment

  • Edit SCENARIOS in simulation.py to try other layouts, such as 4 zones or 3 retries.
  • Raise crash_rate or gray_rate in chaos.py to make the day worse.
  • Change ttl on DnsFrontend to see how DNS caching delays failover.

What the model leaves out

  • The failure rates are made up and compressed: real servers fail far less often than every few minutes.
  • Databases and other shared state become the next single point of failure once servers are redundant.
  • A bad deploy can break every server at once. Canary releases are the usual defense.
  • All three zones sit in one region. Surviving a regional outage needs a second region.
